# Plan: typed Gamend bindings

The engine reaches Gamend through nine calls: `configure`, `login`, `rest`,
`connect`, `join`, `push`, `leave`, `call_hook`, `close`. They are complete
in the sense that every feature Gamend has is reachable, and incomplete in
the sense that a script reaches all but two of them by spelling a URL. This
plan generates the rest: one script function per operation, named, with its
arguments checked and its documentation carried from the server's own, and
each realtime event typed by the channel it came from. Nothing is curated
out, because the next game uses the endpoint this one does not.

## 0. Where the two trees are today

Gamend, read on 2026-09-13:

- `mix openapi.spec.json --spec GamendWeb.ApiSpec` writes
  `clients/godot/openapi.json`, OpenAPI 3.0.0. 243 operations; 98 take a
  JSON body, 93 of those with an inline object schema naming every field;
  99 have path parameters; 55 have query parameters; 194 require the
  bearer token. Responses are typed inline (514 inline objects) or free
  (161). Only four named schemas exist, so there is no model layer to
  generate: every body and reply is a table.
- `proto/gamend_realtime.proto`: 31 messages — `User`, `Lobby`, `Party`,
  `Group`, `MemberEvent`, `KvEntry`, `RpcCall`, `RpcReply`, `RpcError`,
  `ReadyCheckState`, `MatchmakingFound`, `Notification`, `ChatMessage`,
  `QuestProgress`, `WalletChange`, `InventoryChange` among them. The socket
  serves JSON by default and protobuf on request.
- Channels, from `apps/gamend_web/lib/gamend_web/channels/`: `user:<id>`
  pushes `updated` and `friend_updated`, takes `kv:subscribe` and answers
  `kv_updated` / `kv_deleted`; `lobby:<id>` pushes `updated` and
  `user_updated`, answers `get_server_time`; `lobbies` pushes
  `lobby_updated`; `party:<id>` and `group:<id>` push `updated` and
  `member_updated`; `groups` pushes `group_updated`; `signaling` takes
  `offer`, `answer`, `ice`, `list_users`, `broadcast_offer`. Ready checks
  broadcast `ready_check_started`, `_updated`, `_passed`, `_failed`; the
  socket itself pushes `disconnect`. Matchmaking notifies matched users
  through the user channel.
- Its Godot SDK is generated by openapi-generator from the same document:
  `<Tag>Api` classes with one method per `operationId`, every request a
  model class, every call threaded. 52k lines.

The engine, `crates/balaur_gamend`:

- The nine calls, on a worker thread, delivered once per tick at
  `Stage::First`, every arrival an `ExternalIo` completion, so a recording
  replays an online session. `rest(node, method, path, body)` is the
  general call; `login` knows `device_id` and `email`+`password`;
  `call_hook(socket, plugin, name, args)` is the hook RPC over the socket.
- Docs come from `m.module_doc` and `m.describe`, which `scripts/gen_docs.py`
  reads out of a booted engine into `docs/generated/api.json`, and
  `scripts/api_lints.py` checks every function for a doc line, a banned
  abbreviation, a `get_` prefix and a setter without a reader.
- Tests in `crates/balaur_gamend/tests`: an in-process stand-in serving the
  device login, one GET and an echoing hook over a Phoenix-ish socket, plus
  a `live_` test against `mix dev.start` that is ignored by default.
- No generated code is checked into any crate today. The precedent for
  derived files is `docs/generated/`, regenerated by a script with a
  `--check` mode that precommit runs.

What Polyglot Pirates needs from all of this, counted over its own
scripts: 47 hook calls through `rpc_call`, which is `call_hook`; 30 typed
operations, all under parties, quests, lobbies, users, ready checks and
notifications; a KV subscription and its `kv_updated` pushes; party and
lobby channel events; and an auth layer over device, Apple, Discord,
Facebook, Google and Steam sign-in with a saved session. None of it needs
the admin half of the document.

## 1. Design

**One generator, one file, checked in.** `scripts/gen_gamend.py` reads
`openapi.json` and `gamend_realtime.proto` from a path it is given (the
Gamend checkout beside this one, or a downloaded release) and writes
`crates/balaur_gamend/src/generated.rs`. The file is committed, the way
`docs/generated/` is, and `gen_gamend.py --check` fails precommit when it
is stale. A build step was open question 3's other answer; it is rejected
because it would put the Gamend checkout on every contributor's build path
and on CI's. The generator's own input — the two source files — is copied
into `crates/balaur_gamend/spec/` beside the output, so a regeneration is
reproducible from this repository alone and a diff of the spec is a diff of
the API.

**One function per operation, flat under `gamend`.** Script modules are
flat, so `gamend::create_party`, `gamend::quick_join`, `gamend::my_quests`.
The name is the `operationId`, which is unique across the document, with
two mechanical edits so the lints pass: a leading `get_` is dropped
(`get_lobby` is `lobby`, N7), and the admin operations keep their `admin_`
prefix, which is the only prefix the document uses consistently. A name
that collides after the edit is reported by the generator and resolved by
hand in a small table it reads, never silently.

**The signature is the operation's.** Path parameters become leading
arguments in path order; the body's fields, when the schema names them,
become one `params` table whose keys the binding checks against the schema
and refuses with the field name when one is unknown or a required one is
missing; query parameters become an optional trailing `options` table. So
`gamend::quick_join(node, #{ title: "duel", max_users: 2 })` and
`gamend::my_quests(node, #{ category: "daily", page: 1 })`. A free-object
body passes through untouched. Every function returns the id `rest`
returns today and completes the same way, so a script that awaits `rest`
awaits these.

**Events typed per channel, from a table the proto fills.** OpenAPI does not
describe the socket, so the generator keeps a hand-written table of
(channel, event, message) rows — the list in §0, twenty rows — and emits a
constant per event (`EVENT_LOBBY_UPDATED`, `EVENT_KV_UPDATED`,
`EVENT_READY_CHECK_PASSED`, …) and a decoder that turns the payload into a
table shaped by the proto message it names. A push whose event is not in
the table still arrives, as it does today, with `kind = "message"`. The
table is the one thing in this plan a Gamend change can silently miss; the
live test in §4 is what catches it.

**Auth is where the SDK spent its effort, and it stays hand-written.**
Device and email login exist. What is generated is the OAuth operations —
`list_auth_providers`, the session start and poll for each provider — as
plain functions. What is written by hand, once, in `auth.rs`: the flow that
opens the provider's URL through `engine::open_url`, polls the session
until it resolves, and saves the token under `save::`; and the session
restore on `configure`. The SDK's twenty auth verbs collapse to `login`
taking a `provider` and `ticket` alongside the two it takes now, plus
`logout`, `link`, `unlink` and `session`.

**The hook RPC is already right.** `call_hook` is what 47 of the game's
calls are, and its reply shape (`data` or `error`) is what `rpc_call`
unpacks. It gains nothing from generation and is left alone.

**Determinism is unchanged.** A generated function is a `rest` with its
arguments assembled in Rust; the delivery contract, the snapshot and the
replay are the ones the nine calls have.

## 3. Steps

- **1. The generator and the spec.** `scripts/gen_gamend.py`, the spec
  copied into `crates/balaur_gamend/spec/`, `--check`, the precommit step.
  Ends with: the script emits a `generated.rs` that compiles and registers
  243 functions, each with its `summary` from the document as its doc line,
  and `scripts/api_lints.py` passes over the result.
- **2. Arguments.** Path, body and query parameters as §1 says, the
  required-field check, the collision table. Ends with: the in-process test
  server sees `create_party` arrive as `POST /api/v1/parties` with the body
  it was given, and a call with a misspelled field fails before any I/O
  with the field's name.
- **3. Events.** The (channel, event, message) table, the constants, the
  decoders. Ends with: a `lobby:<id>` push of `updated` reaches
  `on_gamend_event` as `kind = EVENT_LOBBY_UPDATED` with a `lobby` table
  shaped by the proto, and a push of an unlisted event still arrives as
  `message`.
- **4. Auth.** The OAuth flow, `logout`, `link`, `unlink`, `session`, the
  restore on `configure`. Ends with: the live test signs in with a device
  id, restarts the engine, and is still signed in.
- **5. The docs.** `python3 scripts/gen_docs.py` picks the new functions up
  from the booted engine with no change; what changes is
  `docs/generated/script-api.md`'s reader, which needs a per-tag grouping
  for a module with 250 functions. Ends with: the reference page reads by
  tag, and the website's reference pipeline (`../balaur-website`,
  `gen-reference.mjs`) renders it.
- **6. The port.** In `../polyglot-pirates-balaur`, `gamend_controller` and
  the client adapter written over the generated calls rather than over
  `rest`: the 30 typed operations by name, `register_kv` as `join` plus the
  KV subscribe push, the presence cache as a table. Ends with:
  `login_offline` and `main_menu_ready` pass with `gamend_controller`
  removed from `port/ported.txt`, and `online_game_start` passes against a
  local `mix dev.start`.

Step 6 does not wait on 1 to 5: the adapter can be written over `rest` and
`call_hook` today and swapped to the names as they land. What it waits on is
someone writing it, which is why it is here as a step and not left implied.

## 4. What CI can prove

- Steps 1 and 2 against the in-process stand-in in
  `crates/balaur_gamend/tests`, which grows a router that records the
  method, path and body of every request and answers from a table, so a
  test asserts the wire shape of any of the 243 without a server.
- Step 3 with the same stand-in pushing each of the twenty events.
- The `live_` test, still ignored by default, runs every generated function
  the game uses against `mix dev.start` and is the check on the event table:
  an event the server sends that the table does not name fails it.
- `gen_gamend.py --check` in precommit, so the checked-in file and the spec
  beside it never drift; and a diff to `spec/` in a pull request is a
  reviewable diff of the API.

## 5. Open questions

1. **Protobuf on the socket.** The server serves it on request and the SDK
   asks for it. JSON is what the engine speaks today and what §1 decodes.
   Asking for protobuf saves bytes and adds a decoder for 31 messages; the
   generator could emit it from the same proto. Not in these steps: the
   game's realtime traffic is small, and the JSON path is the one the
   in-process test server can fake.
2. **Where the spec is copied from.** A checkout beside this one is what
   this plan assumes. A Gamend release could ship the two files as an
   artifact, which is what a contributor without the Elixir toolchain
   needs to regenerate; that is a row for Gamend's own roadmap.
3. **The reference page at 250 functions.** Step 5's per-tag grouping is a
   change to the docs generator that every large module would use; whether
   `physics3d` at 89 wants it too is a question for that step.
