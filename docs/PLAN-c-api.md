# A C API for addons

Status: **Tier 1 shipped.** `crates/balaur_plugin/src/capi.rs` is the
implementation, `crates/balaur_plugin/include/balaur_extension.h` the committed
header, and `examples/extension_c_counter/counter.c` an extension in C that a
Luau script calls. The rest of this document is the reasoning that led there,
kept because the tiers above Tier 1 are still open.

## What shipped, against what was planned

Tier 1 as recommended: an extension registers named script modules of
functions and constants, exchanging `Value`. No ECS type crosses the boundary.

Three decisions came out differently from the sketch below, all for the same
reason -- the direction is *the engine loads the addon*, not *the addon links
the engine*:

- **It lives in `balaur_plugin`, not a separate `balaur_capi` cdylib.** The
  cdylib-plus-header shape is what an addon that drives the engine needs. An
  addon the engine `dlopen`s needs the mirror image, and it belongs next to the
  loader that opens it. `load_extension` now accepts either kind of library,
  chosen by which symbols it exports, so nothing above it changed.
- **A vtable, not exported symbols.** The addon receives a `BalaurApi` of
  function pointers. Resolving symbols back into the host executable needs it
  linked with its dynamic symbols exported, which is neither the default nor
  portable.
- **The header is hand-written, not generated by cbindgen.** It carries
  `_Static_assert`s on every struct size and offset, and a test asserts the
  same numbers from the Rust side. Drift fails both compiles instead of
  appearing in a diff nobody reads.

**The ownership question dissolved.** "String ownership, and an explicit
`balaur_string_free`" turned out to be avoidable: every `BalaurValue` is a
borrowed view valid only for the call it appears in, and the host copies before
returning. No allocation crosses the boundary, so there is no free function and
no allocator question. That is the same call-scoped discipline
`Value::Callback` already used, generalised to every value.

**Why this matters more than the Rust extension path.** A Rust extension needs
the identical rustc on both sides, and even then it cannot reach a resource the
host inserted: resources are keyed by `TypeId`, and two separately compiled
copies of `balaur_core` compute different ones
(`crates/balaur_plugin/tests/extension.rs` measures it). A C extension computes
no `TypeId` at all and holds its state behind its own `void*`, so the ceiling
that applies to the Rust path does not apply to it.

## The seam already exists, and it is the right shape

`balaur_script` was built so a language backend could be added without the
engine naming a language. That is very nearly the same problem as adding a
*C* backend, and it means the first tier of a C API is small:

```rust
pub type BoundFn<C> = Box<dyn Fn(&C, &[Value]) -> Result<Value>>;

pub trait Bindings<C: ?Sized> {
    fn function_raw(&mut self, name: &str, f: BoundFn<C>);
    fn constant(&mut self, name: &str, value: Value);
}
```

`BoundFn` maps almost one-to-one onto a C function pointer:

```c
BalaurValue (*fn)(BalaurEngine*, const BalaurValue* args, size_t argc);
```

`Value` is already flat and already carries nothing borrowed except through
ids — `Node` is an entity's bits, `Callback` is an index valid only for the
duration of the call. Both of those decisions were made for the scripting
seam, and both are exactly what an FFI boundary wants.

## Three candidate surfaces

**Tier 1 — register script modules.** An addon declares a named module with
functions and constants, the same way `balaur_physics` does. Everything it
exchanges is a `Value`. This is the smallest surface that is genuinely useful,
and it is additive: an addon extends what scripts can call.

- Cost: a C mirror of `Value`, one registration entry point, and the plumbing
  below. No ECS types cross the boundary.
- Gets you: native code behind a script API. Image loaders, networking,
  physics queries, platform integrations.
- Does not get you: components, systems, or scene-file vocabulary.

**Tier 2 — components and systems.** Add registering a component type, a
per-frame system, and a scene key. Now an addon is a real plugin.

- Cost: entity ids and component storage cross the ABI, plus a query
  interface. Component data would have to be described (a schema) or passed as
  `Value`, and the cheap version of that is slow, while the fast version pins
  memory layout into the ABI.
- This is the tier where the ABI stops being obviously stable.

**Tier 3 — the whole `App`/`Engine` surface.** Everything a Rust plugin can
do. Not recommended as a starting point: it freezes internals that are still
moving, and every future refactor becomes a compatibility problem.

## What has to be solved regardless of tier

- **`Value` is not `repr(C)`.** A C mirror is needed — a tagged union or a
  handle-based accessor API. A tagged union is faster and uglier; handles
  (`balaur_value_type`, `balaur_value_get_int`, …) are uglier to write against
  but survive `Value` gaining a variant, which it just did (`Many`).
- **String ownership.** Who frees what, and an explicit `balaur_string_free`.
- **Panics must not cross the boundary.** Every entry point wraps in
  `catch_unwind`; a panic unwinding into C is undefined behaviour.
- **Errors.** `BoundFn` returns `Result`; C has no such thing. Either an
  out-param error slot or a sentinel value plus `balaur_last_error`.
- **Callbacks.** `Value::Callback` is valid only during the call that received
  it. That invariant has to be stated loudly, because C gives no help enforcing
  it.
- **Versioning.** A `balaur_abi_version()` the host checks on load, so an
  addon built against an older engine is rejected with a message rather than
  crashing.

## Delivery (settled)

A `balaur_capi` crate with `crate-type = ["cdylib", "staticlib"]`, producing
`libbalaur.{so,dylib,dll}` and a `balaur.h` generated by cbindgen and committed
so drift is visible in review. Built for the desktop targets in `build.yml`
alongside the editor, and smoke-tested by a tiny C program that loads it,
registers a module, and calls one function — the same standard the runtime
template is already held to, where "it compiled" is not the bar.

Loading addons at runtime (the engine `dlopen`ing an addon, rather than an
addon linking the engine) is the mirror image and needs its own decision; the
tiers above describe the API either way.

## Recommendation

Ship **Tier 1** first, behind an explicit `balaur_abi_version()`. It is small,
it reuses a seam that already works, and it answers the question the C API
exists to answer — can someone write an addon in another language — without
freezing the ECS.

Tier 2 should wait until there is a real addon asking for it. The component
and query ABI is the part that is expensive to change once published, and
guessing at it now means guessing at what addon authors need before any exist.

## Open questions

1. Is the goal addons *for the editor* (tools, importers, panels) or addons
   *for games* (native gameplay code)? The answer changes what Tier 2 should
   expose first — the editor is itself a Balaur project, so editor addons may
   be better served by scripts than by C. **Still open.**
2. ~~Tagged union or handle-based accessors for `Value`?~~ **Tagged union.**
   Handles were attractive only because they survive `Value` gaining a variant
   and because they hide ownership. The version check covers the first, and the
   call-scoped borrow rule removed the second, which left no argument for the
   slower and uglier option.
3. ~~Does an addon get loaded by the engine, or does the addon drive the
   engine?~~ **The engine loads the addon**, out of a project's `extensions/`
   directory. The other direction is still unbuilt and would want the
   `balaur_capi` cdylib this document originally described.

## What Tier 1 does not do

Worth stating plainly, because the gap is what a real addon will hit first:

- No components, systems, scene keys, or ECS access — that is Tier 2, and it
  still deserves to wait for an addon that asks for it.
- No calling *back* into script. `Value::Callback` crosses the boundary as an
  id, but there is no `api->invoke` yet, so a C extension cannot run a script
  function it was handed.
- No `Engine` access at all: a C function receives its own `void*` and its
  arguments, and nothing else.
